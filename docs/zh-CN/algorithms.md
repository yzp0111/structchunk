# 算法

[English](../algorithms.md)

## 概述

structchunk 提供两种分块算法。两者都将文本解析为相同的原子块表示，但组装方式不同。

**线性（贪心）**：按文档顺序遍历块，填充每个块直到大小上限。速度快，简单，适合扁平文档。

**层次（章节树）**：从文档的标题结构构建一棵树，自底向上遍历，每个章节生成一个块。默认算法。生成的块始终从章节标题开始。最适合技术文档、报告和书籍。

两者共享相同的子分块器、路径构造、上下文吸收和后处理管道。

## 线性算法

线性算法（`chunk_linear`）使用贪心的逐块组装：

1. 将文本解析为原子块。
2. 按文档顺序遍历块。累积到一个组中，直到总大小超过 `max_chunk_size`。
3. 当下一个块会超出容量上限时，向后扫描最后一个标题并在该处切分（**标题前置**）。
4. 过大的块交由类型特定的子分块器处理。
5. 计算每个组的 RAG 路径。
6. 上下文吸收：当一个 TABLE 或 LIST 开始一个新组时，向后扫描最近的非空、非 table/list 块，如果它在 `hard_max_size` 内则将其吸收。
7. 后处理：重新切分那些正文加上注入路径后超过 `hard_max_size` 的块，注入缺失路径，合并同一路径的小块，丰富元数据。

适用于没有严格章节结构的扁平文档，或者当你希望对切分点进行精细控制时使用。

## 层次算法

层次算法（`chunk_hierarchical`）构建并遍历章节树：

1. 将文本解析为原子块。
2. 构建 `_Section` 节点的树。每个章节由一个标题及其内容块和子章节组成。
3. 通过 `_section_to_chunks` 自底向上遍历树。
4. 叶子章节（无子章节）：如果内容在 `max_chunk_size` 内，则生成一个块（`is_section_complete=True`）。否则，进行子切分并生成多个块（`is_section_complete=False`）。
5. 内部章节（有子章节）：先处理子章节，然后将父章节内容与第一个子章节合并（如果全部能容纳）。
6. 相邻的同级兄弟节点被贪心地合并，但受限于章节完整不变量：完整的章节可以合并；被切分章节的尾部不能合并。
7. 后处理与线性算法相同。

结果是：每个块都属于一个章节，标题位于其内容之前，不会出现表格尾部与下一章节标题混杂的情况。

## 对比

| 方面 | 线性 | 层次 |
|---|---|---|
| 策略 | 贪心逐块 | 章节树自底向上 |
| 是否需要标题 | 否 | 是 |
| 块边界 | 基于内容大小 | 基于章节边界 |
| 速度 | 较快 | 略慢 |
| 默认 | 否 | 是 |

## 子分块器

当一个原子块单独超过 `max_chunk_size` 时，它会被交由类型特定的子分块器处理：

**段落**（`split_paragraph_at_sentences`）：在句子边界处切分。每个句子保持完整。URL 和电子邮件地址得到保护，因此内部点号不会触发错误的切分。如果某个句子超过 `hard_max_size`，则 `_force_split_long_strings` 回退方案会在字符边界处切分。

**表格**（`split_table_rows`）：在行边界处切分。列标题会前置到每个后续块中。

**列表**（`split_list_items`）：在条目边界处切分。每个条目（以 `-`、`*` 或 `1.` 开头及其后续行）保持完整。

**代码**（`split_code_block`）：在行边界处切分。每个片段会重新打开和关闭围栏。

**`force_split_long_strings`**：最终回退方案。当单个句子、表格单元格、列表项或代码行超过 `hard_max_size` 时，此函数在任意字符边界处切分。

可以通过配置标志按类型禁用子切分：`sub_split_paragraph`、`sub_split_table`、`sub_split_list`、`sub_split_code`。

## 句子边界切分

句子边界正则表达式定义在 `_parser.py` 中，同时处理中文和英文：

```
[^.!?。！？]+[.!?。！？]+\s*|[^.!?。！？]+\s*$
```

该模式匹配（1）一系列非终止符字符后跟终止符和可选空白，或（2）没有终止符的尾部片段。

**URL 和电子邮件保护**：在切分前，`_protect_urls` 将 URL 中的内部点号（`api.openai.com`）、电子邮件地址、版本号（`v1.2.3`）、文件名（`docs/api.md`）、函数调用（`obj.method(`）和点号分隔序列（`foo.bar.baz`）替换为 Unicode 占位符（一点引导符 U+2024）。这可以防止正则表达式将每个点号视为句子终止符。切分后，`_restore_urls` 将其恢复。

**单句完整性**：单个句子永远不会被打破。子分块器累积完整的句子，直到达到大小上限。如果某个句子超过 `hard_max_size`，则 `_force_split_long_strings` 回退方案会在字符边界处切分。

## 标题前置

当线性算法即将切分一个组时，它会向后扫描最后一个标题。如果找到（并且其前面的部分满足 `min_chunk_size`），则切分点会移到该标题之前。这保证了标题位于其内容之前，而不是挂在前面块的末尾。

层次算法不需要显式的前置操作：章节由它们的标题定义，因此每个块自然地从标题开始。

然后，第二轮处理会遍历相邻组，将尾部的标题从一个组的末尾移到下一个组的开头。如果最后一个组只包含标题，则将其合并到前一个组中。

## 上下文吸收

当 TABLE 或 LIST 开始一个新的块组时，算法会向后扫描最近的非空块（该块本身不是 TABLE 或 LIST）。如果它在 `hard_max_size` 内，则将其前置。

例如，紧接在表格之前的段落如 `**首选：XXX**` 或 `Important notice.` 会被吸收为上下文摘要。这样 RAG 嵌入就能将段落与表格数据一起处理。

两种算法都共享此功能。线性算法在组装阶段（`assemble_chunks`）完成。层次算法的叶子切分路径使用 `_extract_intro_text` 将前一段的最后一个句子转发到后续块中。

## RAG 路径

每个块携带一个 `header_breadcrumb` 字段：一个包含 markdown 级别前缀的标题字符串列表，如 `['# H1', '## H2', '### H3']`。

路径分两步构建：

1. **组末尾路径**：从组之前存在的标题栈开始，然后使用标准标题栈语义（更深的标题压栈；同级或更高级别的标题弹栈）应用组内所有标题。这会产生正确的末尾状态路径，没有陈旧的同级标题。

2. **剥离并重新添加**：弹出组末尾路径的最后一项，然后按**文档顺序**添加组内出现的所有标题。这避免了陈旧的同级标题（例如 `表1` 泄露到 `表2` 的块中）和错误的顺序（例如 `场景4` 出现在 `场景3` 之前）。

## 缺失路径注入

组装完成后，`inject_missing_breadcrumbs` 遍历每个块，检查每个 `header_breadcrumb` 条目是否已经存在于块的内容中。条目与剥离后的内容行进行匹配，以避免共享前缀带来的误匹配（例如 `## Section 2` 不会匹配 `## Section 2.5`）。

对于每个缺失的条目，标题行会被前置。每个块都变得自包含：即使是深层嵌套的后续块，其文本中也携带完整的祖先路径。H1 文档标题包含在每个块中，因此没有块会在上下文上被孤立。

注入运行两次（在 `_re_split_with_prefix_budget` 之前和之后），以处理路径注入后重新切分的块。

## 层次兄弟节点合并

自底向上处理后，`_section_to_chunks` 为父章节生成一个块列表。来自同一父章节子节点的相邻块是贪心合并的候选。

合并强制执行**章节完整不变量**：

- 表示**完整**章节的块（`is_section_complete=True`）可以与相邻的同级兄弟节点合并。
- 来自被切分章节的**残余/尾部**块（`is_section_complete=False`）不能与不同兄弟节点的内容合并，即使路径共享共同前缀。

这防止了一个章节的尾部错误地吸收另一个章节的开头。例如，一个很长的 `## Section A` 溢出到第二个块时，不能吸收 `## Section B` 的第一个块。

在内部，每个生成的块携带一个 `is_section_complete` 标志。作为单个块生成的章节为 `True`；跨多个块切分的章节的所有片段都标记为 `False`。合并器在允许跨章节合并之前会检查两边的该标志。

合并使用路径的最长公共前缀（LCP）比较。这允许跨层级的兄弟节点合并（例如 `## A` 和 `## B` 共享公共祖先 `# Title`），同时保留 H1 边界（不同的 H1 的 LCP 为 `[]`，不能合并）。
